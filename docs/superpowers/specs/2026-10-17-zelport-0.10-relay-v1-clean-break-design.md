# Zelport 0.10 clean break and Relay Protocol v1 design

## Purpose

Establish Zelport as a clean product and protocol namespace with no compatibility
layer for pre-Zelport clients. The resulting source trees, generated artifacts,
documentation, product metadata and supported binaries must contain only Zelport
names. Git history is explicitly outside this change. Immediately before
publishing Zelport `v1.0.0`, each repository's default branch will be rewritten
onto a new root commit containing the approved `v1.0.0` tree. All earlier
commits, branches, tags and releases under Zelport's control will be removed in
that separately approved operation. Already published module proxies, checksum
databases and other third-party caches may retain pre-1.0 source indefinitely;
the later history cleanup does not claim to erase those external records.

The canonical product version is `0.10.0`. Contexts that conventionally prefix
versions with `v` use `v0.10.0`. The relay wire protocol starts at version `1`
and uses the `zelport-relay/v1` cryptographic namespace.

## Scope

This change coordinates the sibling repositories in the local Zelport workspace:

- `zelport-sdk-go` owns the relay wire version and cryptographic contexts.
- `zelport-relay` consumes SDK v0.10.0 and accepts only wire version 1.
- `zelport` consumes SDK and relay v0.10.0 and persists only version-1 relay
  records and digest watermarks.
- `workspace` coordinates verification and prevents the retired brand from being
  reintroduced.
- `zelport-installer` owns the canonical installer, its tests, CalVer releases
  and synchronization to the website.
- `zelport-omarchy`, distribution metadata and active documentation use product
  version 0.10.0 without preview labels.
- the installer pins Zelport App 0.10.0 but releases independently.

The identity kit and website have no independent runtime version unless an
existing package manifest requires one. External dependency versions and Go
language versions do not change. The Zelport configuration schema resets to
version `1` as part of the clean break.

The two unused hypothetical top-level project scaffolds are removed from the
workspace. No surviving source, documentation, build configuration or project
index may name them, reference them or anticipate their APIs. A future hosted
product would require a new design and repository decision from first
principles; this codebase reserves no boundary for it.

## Product terminology and composition

**Zelport** is the product family. **Zelport App** is the main locally running
application distributed as the `zelport` executable and package. Zelport App is
a local HTTP reverse proxy application with integrated service-source modules
and Built-in Relay for end-to-end encrypted connections between remote Zelport
App instances.

**Zelport Relay** is the standalone relay server distributed as the
`zelport-relay` executable. **Ports over Relay** is one of Zelport App's
service-source modules and acts as a relay client. It uses the relay protocol
and client SDK. **Built-in Relay** is the relay server capability inside Zelport
App. Built-in Relay and Zelport Relay use the same relay server implementation.

Zelport App's modules are internal architectural boundaries for source
ownership, dependency isolation, lifecycle management and verification. They are
not product editions and are not presented as a user-selectable build system.
The standard distributed Zelport App contains every implemented feature module:

- Docker Sandboxes;
- Containers;
- Local Ports;
- Remote HTTP;
- Ports over SSH;
- Ports over Relay;
- Built-in Relay.

Build tags and the `zelport-core` executable exist only for development,
dependency-boundary checks, tests and diagnostics. They are not separately
marketed or distributed user products. Ordinary `go build ./cmd/zelport`,
`go install`, `make build` and every user-facing installation path produce the
complete Zelport App. A dedicated `zelport_core` build tag selects the diagnostic
core-only build; combining it with individual module tags supports the boundary
matrix. Release builds never use `zelport_core`.

The retired architectural term for the whole application or listener is removed
from source, documentation, UI, tests and identifiers. Public text uses
**Zelport App**, **Zelport instance**, **Zelport service**, **reverse proxy**,
**listener**, **Localhost port** or **endpoint**, according to meaning. Internal
APIs use precise resulting names including `ListenerAuthority`,
`ProxyOptions.ListenerAuthority` and `SelfTarget` listener parameters. The UI
endpoint element uses `endpoint`, and the Omarchy setup document is named
`ZELPORT_SETUP.md`.

## Domain terminology

Every implemented capability related to `ports_over_relay`, relay admission,
relay transport, encrypted relay catalogs, peer traversal or relay-based remote
administration uses the term **relay** exclusively. This applies to source paths,
Go package names and aliases, functions, tests, errors, HTTP headers, scripts,
documentation, CSS classes, JavaScript identifiers, tab IDs and URL fragments.

The resulting relay-domain names include:

- `PORTS_OVER_RELAY.md`;
- `docs/ports-over-relay-v1.md`;
- `docs/ports-over-relay-verification.md`;
- `internal/relay/integration`;
- `scripts/relay-demo.py`;
- the `#relay` module tab and relay-named UI identifiers;
- `X-Zelport-Relay-Trace`.

There are no aliases or redirects for the retired names. Unrelated external
proper nouns retain their real names.

## Protocol identity

`protocol.Version` becomes `1`. Every encoded or persisted relay protocol value
that currently identifies wire version 3 becomes version 1, including:

- relay routes;
- catalog records and envelopes;
- peer contexts;
- authenticated catalog data;
- accepted-record validation;
- persisted digest watermark versions.

The only relay WebSocket endpoint is `/v1/ws`. The SDK always dials this path,
Zelport Relay and Built-in Relay serve only this path, and relay URL validation
accepts only an empty path, `/` or `/v1/ws`. Earlier versioned endpoint paths are
rejected and are never normalized or redirected.

The SDK centralizes the protocol identity so that the wire version and
cryptographic contexts cannot drift. The exact contexts are:

- `zelport-relay/v1`
- `zelport-relay/v1/catalog`
- `zelport-relay/v1/client-relay/`
- `zelport-relay/v1/client-relay/open/`
- `zelport-relay/v1/consumer-provider/`
- `zelport-relay/v1/renewal/`

There is no fallback, negotiation, alias, migration or diagnostic branch for the
retired protocol. Version-3 inputs fail ordinary version validation. The complete
Zelport configuration schema resets to version `1`; every other schema version is
rejected without being rewritten. Persisted Ports over Relay settings additionally
carry a required protocol marker with value `1`; missing or different markers are
rejected with a precise configuration error.

Existing configurations are not imported or converted. Routes, module settings,
Ports over Relay identities, credentials, imports, peer history, encrypted
catalogs, sessions and digest watermarks are recreated from a fresh configuration.
Standalone and Built-in Relay admission credentials are also regenerated.

## Product versions

The canonical SemVer product version is `0.10.0`. The `v` prefix is a
contextual representation, not part of the numeric version. Git tags, Go module
versions, release names and human-facing version labels use `v0.10.0`. Manifest
fields and other machine-readable fields that expect plain SemVer use `0.10.0`.
Specifically:

- SDK Git tag and Go module version: `v0.10.0`
- relay Git tag and Go module version: `v0.10.0`
- Zelport App Git tag and release name: `v0.10.0`
- Omarchy integration Git tag: `v0.10.0`
- Omarchy integration manifest: `0.10.0`
- installer release pin: `0.10.0`
- installer version: CalVer `YYYYMMDD.N`; script value `20261017.1`, Git tag and
  GitHub release `v20261017.1`
- Homebrew formula version: `0.10.0`, with release URLs referring to tag
  `v0.10.0`; packaging-only fixes use Homebrew's numeric `revision` and the
  rolling `homebrew-tap` repository has no independent release version or tags
- human-facing version label: `Zelport v0.10.0`

Product and API documentation must no longer describe the release as preview.
This implementation includes coordinated publication after every local change,
test, artifact and checksum has passed final verification. It may push prepared
commits, tags and release artifacts to the existing Zelport repositories and
create the approved `zelport-installer` repository in the Zelport organization.
It does not authorize force pushes, tag replacement, any other repository
creation or deletion, or visibility changes.

Before remote tags exist, the exact SDK and relay module sources are staged in a
local file-based Go proxy. Each module archive is generated with Go module ZIP
rules from a clean committed tree, records its expected module checksum and is
served as `v0.10.0`; local pseudo-versions and `replace` directives are forbidden.
Consumers are verified with workspace resolution disabled against that proxy.
After each tag is published, a fresh public download must produce the same module
checksum before the dependent repository may be published.

Release publication must follow dependency order: SDK, relay, Zelport App,
Omarchy integration, Homebrew, standalone installer, then installer website
synchronization. Distribution files prepared by this change are release-candidate
metadata until their publication step: they are internally self-consistent, but
their public URLs are not expected to resolve beforehand. A checksum is recorded
only from the exact local artifact that will be uploaded; neither URLs nor
checksum values are fabricated.

## Publication sequence and safety

Publication begins only after an all-repository preflight confirms:

- every intended source change is committed with the required identity and all
  unrelated working-tree changes remain preserved;
- the complete local verification and cleanliness suite passes;
- every release artifact and checksum exists and matches its metadata;
- authenticated push and release access exists for every target repository;
- the intended remote branches have not diverged; and
- no target `v0.10.0` or installer `v20261017.1` tag or release already exists.

All repository unit, race, vet, integration, JavaScript, build, packaging,
cleanliness and release-artifact checks defined by this design are mandatory and
must pass. A failed mandatory check cannot be accepted as a known failure. A
check that genuinely requires unavailable external hardware or infrastructure
must be identified as environment-specific before tagging; skipping it requires
the user's explicit waiver naming that exact check and its missing prerequisite.
No other test waiver is permitted.

The publication sequence is:

1. Push the SDK commit and `v0.10.0` tag, then verify that a clean
   `GOWORK=off` consumer can resolve the public module.
2. Push the relay commit and `v0.10.0` tag, then verify its SDK dependency and
   public module resolution.
3. Push the Zelport App `v0.10.0` tag without updating its main branch, create
   the GitHub release and upload the exact verified platform archives and
   checksum manifest. Verify every asset, then push the prepared Zelport App main
   branch before any distribution reference is published.
4. Push the Omarchy integration commit and `v0.10.0` tag, create its GitHub
   release and upload the exact verified integration bundle and checksum.
5. Push the Homebrew formula only after every referenced Zelport App release
   asset is publicly downloadable and checksum-valid.
6. Publish the `zelport-installer` commit and `v20261017.1` tag, create its GitHub
   release, and attach the exact verified `install.sh` and checksum manifest.
7. Allow the installer repository's release workflow to synchronize that exact
   released script to the website. Then verify matching source, release asset,
   website repository and public installer SHA-256 values.

Each dependency publication is verified before its consumer is published. A
failure stops the sequence without rewriting or deleting already published
history; the exact completed and pending stages are reported before resuming.

## Documentation and artifact cleanup

Documentation cleanup is a separate review gate before implementation edits any
existing document. The review produces a complete inventory of current
documentation, implementation plans, specifications, verification reports,
benchmarks and captured output. For each path it records the document's purpose,
whether it still describes a supported system, the proposed action
(`keep`, `rewrite`, `rename` or `delete`) and the reason. The user approves the
disposition document by document; no existing document is changed or removed
before its disposition is approved.

Clearly historical artifacts are pre-approved for deletion without individual
review prompts. This includes dated benchmark reports and raw profiles, captured
verification results, completed implementation plans and ledgers, superseded
design proposals and obsolete upgrade notes. The current clean-break design is
not historical and remains the controlling specification. Any still-valid
requirement is transferred to an approved current specification, test or living
backlog before its historical container is removed.

As the default policy after that review, obsolete plans and captured results are
deleted rather than cosmetically rewritten when doing so would falsify their
historical meaning. Current protocol, operation and installation documentation
is rewritten for Relay Protocol v1 and Zelport product version 0.10.0. This
design specification remains as the approved record of the clean break.

`zelport/TODO.md` remains a living, non-binding backlog. Its valid App and Arch
packaging ideas are rewritten for Zelport terminology and configuration schema
v1, transient publication-status claims and compatibility work are removed, and
installer service-adapter ideas move to `zelport-installer/TODO.md` so each item
has one repository owner.

The historical `zelport/docs/REPOSITORY_INTENT.md` is deleted without a
replacement. Current repository purpose and architectural boundaries are owned
by the App README, `DESIGN.md` and `docs/MODULES.md`; a second repository-intent
summary would duplicate and eventually drift from those authorities.

The historical `zelport/docs/implementation.md` MVP ledger is also deleted
without a replacement. Durable implementation constraints belong in current
design and module documentation and executable tests, not in a completed-task
log tied to an old branch and one-off local verification session.

The dated `zelport/docs/modularization-verification.md` capture is deleted, not
rewritten. Module boundaries and contracts remain in their authoritative design
documents and automated build matrix; any retained `0.10.0` verification record
is generated only from a new run and stored as a dated file under
`docs/verification`.

The dated catalog-compression benchmark document and its raw size and CPU output
are deleted. They measure the retired protocol and are not relabeled as Relay
Protocol v1 evidence. Compression behavior stays covered by the normative
protocol specification and tests; any published v1 measurements come only from
a new benchmark run with new dated output.

The dated idle-catalog benchmark and its before, after and lifecycle raw output
are deleted for the same reason. The `known`-hint semantics and HTTP compression
passthrough remain in the protocol specification and executable tests. Compact
authenticated freshness records and separate-host benchmarks move to the living
backlog as uncommitted Relay performance ideas.

The remaining dated relay admission and protocol-v3 benchmarks, their raw output
and profiles, all captured `docs/verification` results, completed plans under
`docs/superpowers/plans`, the superseded cloud administration and catalog-renewal
designs, obsolete App and Relay upgrade notes, the old Ports over Cloud
verification record, the Arch source-package verification capture and Omarchy's
native-results capture are historical artifacts and are deleted under the same
policy. Current operational documents that linked to them are rewritten without
those historical references.

The canonical `install.sh`, its tests, documentation and website synchronization
workflow move from the Zelport App repository into `zelport-installer`; they are
removed from the App repository rather than retained as duplicate sources. The
website copy remains generated and is never edited manually.

The Arch Linux source-package generator, tests, templates, checked-in recipe and
operational documentation are consolidated under `zelport/contrib/archlinux`;
the generic `contrib/distribution` directory is removed. This packaging belongs
to Zelport App and remains distinct from the `zelport-omarchy` integration. Its
published package version follows Zelport App `0.10.0`; it has no preview-version
conversion or independent CalVer lifecycle. The old source-package verification
capture is deleted rather than rewritten. A new
`contrib/archlinux/VERIFICATION.md` is created only from the actual `0.10.0`
package checks and states every tested and untested target explicitly.

`homebrew-tap/README.md` remains the tap's concise installation and maintenance
guide. It documents Zelport App version `0.10.0`, Homebrew `revision` for
packaging-only fixes, exact published release assets and an unpublished `0.0.0`
local fixture. It assigns no version or release tags to the rolling tap, does not
depend on `zelport-installer`, and does not present supported third-party tools

`zelport-identity-kit/README.md` remains the authoritative visual-identity and

`zelport-web/README.md` remains the website build and local-development guide.

`zelport-omarchy/README.md` remains the integration's concise user and developer

App terminology. The integration never installs, starts or configures the App.
Current polling, validation, stale-state and API trust boundaries remain; local
development uses a neutral `0.0.0` fixture rather than product prerelease labels.

`zelport-omarchy/docs/CONFIGURATION.md` remains the authoritative **Zelport

`zelport-omarchy/docs/GATEWAY_SETUP.md` is renamed to `ZELPORT_SETUP.md` and

loopback client restrictions and the integration's non-owning lifecycle boundary.
Windows internals, preview-token migration, old flags, runtime descriptors,

`zelport-omarchy/docs/NATIVE_ACCEPTANCE.md` remains a reusable mandatory release

rebuilt from current source as:

- `zelport`
- `zelport-relay`

Historical PoC, UI-test and one-off diagnostic executables without current build
targets are deleted and not replaced. Platform release archives retain the
project's existing `zelport_<version>_<os>_<arch>` naming convention.

## Regression guard

The workspace gains a product-and-domain-cleanliness check. Its configured roots
are the workspace coordination files and every surviving Zelport project:
`zelport`, `zelport-sdk-go`, `zelport-relay`, `zelport-omarchy`,
`zelport-installer`, `homebrew-tap`, `zelport-identity-kit` and `zelport-web`. It
fails if a removed top-level scaffold still exists. Under those roots it scans
every tracked, untracked and ignored path except `.git`, including generated
files and release artifacts. It checks both path components and file bytes for:

- the retired product token;
- the obsolete relay-domain token when it names an internal Zelport capability;
- the retired whole-application or listener token;
- names of the removed scaffolds; and
- preview or other prerelease qualifiers in active product-version metadata.

For ZIP and compressed tar release archives, the check scans archive member
paths and decompressed regular-file contents in addition to the archive's raw
bytes. For executables and other binary files it scans raw printable byte
sequences. Product prerelease validation is restricted to known version and
release metadata fields; ordinary uses of words such as UI preview controls are
not version violations.

The prohibited names are assembled from parts so the check does not contain or
reintroduce them itself. Every exception is an exact path-and-token pair in a
reviewed allowlist. Allowlisting is permitted only for genuine external proper
nouns or verbatim third-party license/dependency material; directory-wide,
extension-wide and Zelport-owned identifier exceptions are forbidden.

The check is included in the shared verification target, reports every offending
path and token category, and returns nonzero if any violation or unreadable
in-scope file remains. Git object storage and history are the only content
excluded from the scan because history rewriting is deferred to the separate
pre-`v1.0.0` operation. The generated website installer is verified after the
installer repository's release synchronization workflow rather than edited
manually.

## Test strategy

Implementation follows test-driven development:

1. Change focused relay protocol tests to require version 1 and the new
   cryptographic contexts, and confirm that they fail against the current
   implementation.
2. Centralize and update the protocol identity with the minimum code needed to
   pass those tests.
3. Update relay and Zelport App tests to serve and dial only `/v1/ws`, encode,
   accept and persist only version 1, and require configuration schema version 1
   plus the relay settings marker. Prove that earlier endpoint paths, every other
   configuration or marker version and version-3 inputs are rejected without
   migration or automatic rewriting.
4. Rename every implemented relay-domain path and identifier to relay
   terminology, and verify that routing, UI navigation and trace validation use
   only relay terminology.
5. Inventory documentation and obtain a document-by-document disposition before
   changing or deleting any existing document.
6. Add and exercise the workspace product-and-domain-cleanliness guard.
7. Apply the approved document dispositions, remove generated artifacts, then
   rebuild only the distributed binaries and the development executable required
   for verification.
8. Verify that ordinary direct Go builds, Make targets and packaging produce the
   full seven-module Zelport App, while `zelport_core` and individual module tags
   produce only the documented diagnostic boundary builds.
9. Run SDK, relay and Zelport App unit and race tests and vet; run the relay
   integration harness, feature-module boundary matrix, JavaScript tests,
   packaging checks, distributed builds and the development boundary build.
10. Build clean committed SDK and relay module archives as exact `v0.10.0`
    versions, verify consumers through the local proxy with `GOWORK=off`, and
    record the expected module checksums.
11. Scan the final working trees and rebuilt binaries and archives for the retired
    identity, removed project references and incorrect terminology in the relay
    domain.
12. Run the standalone installer tests and verify its `20261017.1` script version,
    `v20261017.1` repository tag and release assets independently of its Zelport
    release pin `0.10.0`.
13. Run the complete publication preflight, publish in dependency order and
    verify every public module checksum, release asset, formula reference and
    installer copy.

The existing unrelated Zelport App working-tree changes must be preserved. No task
may discard, reset or overwrite them.

## Completion criteria

The change is complete when:

- current working trees outside `.git` contain no retired product token in paths
  or bytes;
- protocol version 1 and the `zelport-relay/v1` namespace are used consistently;
- configuration schema version 1 is the only accepted Zelport configuration
  format, and no migration or automatic rewriting exists;
- `/v1/ws` is the only relay endpoint, version-3 protocol inputs and old persisted
  relay state are rejected, and no compatibility or migration code exists;
- implemented relay functionality uses relay-domain names exclusively;
- product text and identifiers consistently distinguish Zelport App, its reverse
  proxy role, Ports over Relay, Built-in Relay and standalone Zelport Relay;
- the retired whole-application architectural term is absent from current paths
  and file bytes;
- standard user builds contain every implemented module, while partial builds
  remain development and verification tools only;
- the unused hypothetical project scaffolds and every reference to them are
  absent from the workspace;
- active product metadata uses canonical version `0.10.0`, applies the `v` prefix
  only in the defined contexts and contains no preview qualifiers;
- the installer reports CalVer `20261017.1` and pins Zelport release `0.10.0`;
- `zelport-installer` is the sole editable installer source and its
  `v20261017.1` release contains the exact verified script and checksum manifest;
- distributed binaries have Zelport names and contain no retired product identity;
- every mandatory check in the coordinated verification suite passes, and every
  skipped environment-specific check has the user's explicit named waiver;
- SDK and relay `v0.10.0` modules resolve publicly without a workspace or local
  proxy and match the expected local module checksums;
- Zelport App and Omarchy `v0.10.0` releases contain exactly the locally verified
  artifacts and checksum manifests;
- the Homebrew formula resolves only published checksum-valid assets;
- the installer source, release asset, generated website repository copy and
  public installer have matching SHA-256 values;
- every existing documentation file has an approved and applied disposition; and
- all intended commits, `v0.10.0` tags and installer `v20261017.1` tag are
  published without force pushes, tag replacement or repository visibility
  changes.
