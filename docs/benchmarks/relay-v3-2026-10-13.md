# Relay v3 HTTP transport benchmark

For subsequent admission optimizations, see the [staged comparison](relay-admission-2026-10-13.md).

Measured on 2026-10-13 using Apple M4 Pro, macOS arm64, Go 1.27.2,
GOMAXPROCS 14. This is a same-machine loopback baseline, not a WAN benchmark
or a relay capacity guarantee. The working tree had no committed revision.

## Path and method

The harness uses the production cloud client and relay server:

HTTP consumer → yamux / peer Noise v3 → admission Noise / WS or WSS →
separate relay process → admission Noise / WS or WSS → peer Noise / yamux
provider → TCP HTTP backend.

Both clients and the controlled backend run in the parent process. The relay
runs in a separate subprocess so its CPU and allocation counters exclude the
clients and backend. Connections use actual loopback TCP sockets. WSS certificates
are verified against an isolated test trust root. All credentials, catalogs and
services are temporary; the running user's configuration and relay are untouched.

This covers the complete cloud transport carrying HTTP, including admission,
peer encryption and multiplexing. It does not instantiate two full Snitzel
applications: the registry substitutes a controlled backend for module routing,
configuration, discovery, administration and gateway reverse-proxy processing.

Each request opens a new yamux stream and backend TCP connection. HTTP keep-alive
and compression are disabled. One warm-up request establishes sessions outside
timing. Payloads are random bytes; response status and body length are checked.
Concurrency is one or eight requests within one provider/consumer pair, not eight
devices. Each case runs for approximately three seconds, repeated three times.
The tables contain medians across those runs, including the median of each run's
latency percentiles (not a pooled percentile).

CPU seconds per elapsed second: 1.0 means one fully utilized CPU core. At
concurrency eight, aggregate ns/op is not individual request latency.

## Relay network and allocation cost

Ingress and egress are separately divided by useful response body bytes. Each
includes request traffic, headers, control messages and protocol framing across
both clients. Counting occurs below TLS and WebSocket processing but above TCP/IP:
TCP/IP headers, ACK packets and retransmissions are excluded. A forwarded byte
normally contributes once to ingress and once to egress; adding these ratios is
not the same as per-direction overhead.

Allocation KiB/request measures total allocated bytes, not retained memory.
Writes are Go connection Write calls, not measured packets or system calls.

| Transport | Body | Concurrency | Ingress/body | Egress/body | Allocated KiB/request | Allocations/request | Writes/request |
|---|---|---:|---:|---:|---:|---:|---:|
| WS | 1 KiB | 1 | 4.078 | 3.608 | 65.2 | 1867 | 120.5 |
| WS | 1 KiB | 8 | 3.747 | 3.336 | 57.5 | 1631 | 105.2 |
| WS | 1 MiB | 1 | 1.018 | 1.015 | 4002.0 | 13207 | 885.9 |
| WS | 1 MiB | 8 | 1.018 | 1.014 | 3984.4 | 12684 | 851.2 |
| WSS | 1 KiB | 1 | 6.661 | 6.191 | 65.3 | 1866 | 120.3 |
| WSS | 1 KiB | 8 | 6.222 | 5.792 | 60.1 | 1708 | 110.2 |
| WSS | 1 MiB | 1 | 1.042 | 1.035 | 4076.7 | 13351 | 924.8 |
| WSS | 1 MiB | 8 | 1.040 | 1.033 | 4038.7 | 12837 | 891.1 |

The 1 MiB cases reach roughly 142–172 MB/s with 1.28–1.55 relay CPU cores.
Their egress/body ratio is about 1.014–1.035. Small responses have much higher
relative overhead, including fresh stream/connection setup: approximately
105–120 relay writes per request and 3.3–6.2 egress bytes per useful response
byte. These results support profiling admission framing and allocation ownership
before attempting tunnel compression. They do not isolate a bottleneck or prove
any particular optimization's savings.

Relay allocation volume for a 1 MiB response is approximately 4 MiB. End-of-run
live Go heap snapshots range from 0.66 to 3.33 MiB; these are GC-dependent snapshots,
not peak RSS, a memory budget, or a per-tunnel capacity estimate. Default Go
benchmark B/op and allocs/op columns measure the parent process; only columns
prefixed relay- describe the relay process.

## Reproduction

From the repository root on macOS or Linux (loopback listeners required):

```sh
go test ./internal/cloud/client -run '^$' -bench '^BenchmarkRelayHTTP$' -benchtime=3s -count=3
```

See [the harness](../../internal/cloud/client/relay_benchmark_test.go) and
[raw output](relay-v3-2026-10-13.txt). A separate race smoke check can use:

```sh
go test -race ./internal/cloud/client -run '^$' -bench '^BenchmarkRelayHTTP/(WS|WSS)/1024B/concurrency1$' -benchtime=1x -count=1
```

Never compare race-enabled performance figures with the baseline.

## Limits and next measurements

- Clients, relay and backend share the same CPU and loopback network. Results
  are workload observations, not relay-only saturation limits or Internet speeds.
- WSS terminates TLS directly in the relay worker. An external TLS proxy would
  move that CPU cost and introduce another hop.
- Warm sessions exclude initial handshakes and cold connections. Short samples
  do not characterize long-running renewal, reconnects or memory stability.
- No network loss, WAN RTT, slow readers, upload-heavy traffic, application
  WebSocket upgrades or many-device catalog scaling are exercised.
- Metrics sampling adds a small amount of process work. No CPU profile or
  uninstrumented comparison was collected; causality remains unproven.
- Next compare direct HTTP and full gateway routing, capture relay CPU/allocation
  profiles, then repeat over separate hosts with controlled RTT and loss. Test
  any framing/buffer change with the same matrix and security/lifecycle tests.
